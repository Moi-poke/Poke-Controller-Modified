## 1. 前提（プロジェクトの契約）

### 4.1 打切りで止めた live worker を起こし直す（command_runner.py）

**元の欠陥**: 停止が 30 秒終わらないと `_fence_live` が `discardLive`＋`stopLiveWorker` を呼ぶが、戻す経路が無かった。live 経路は姿勢を積むだけで同期送信しないため、以後の実行は「実行中」に見えるのに 1 バイトも出ない。

```python
    def _resume_fenced_live(self) -> None:
        """塞ぎで止めた live worker を起こし直す。

        起こす前に 2 つ片付ける。どちらも「古い実行の持ち越し」を断つため。

        1. 塞いでいる間に溜まった申告を捨てる（discardLive）。
        2. 押しっぱなしを解く（releaseAll）。古いスレッドが最後に押した
           ボタンは Sender の合成状態に残っており、そのまま起こすと新しい
           コマンドが古いボタンを押したまま始まる。

        さらに、止まりきっていない worker が残っていると startLiveWorker は
        何もせず False を返し、_live_stop も消さないため、あとで自然に死んでも
        誰も起こせず無音のままになる。少し待ってから起こし直す。
        終了処理中は起こさない（closeSerial が止める側だから）。
        """
        resume, self._fenced_live = self._fenced_live, False
        if not resume or self._closing:
            return
        ser = self._ser
        try:
            capable = getattr(ser, "isLiveCapable", None)
            if not callable(capable) or not capable():
                return
            discard = getattr(ser, "discardLive", None)
            release = getattr(ser, "releaseAll", None)
            running = getattr(ser, "isLiveWorkerRunning", None)
            stopper = getattr(ser, "stopLiveWorker", None)
            starter = getattr(ser, "startLiveWorker", None)
            if callable(discard):
                discard()
            if callable(release):
                release()
            if not callable(starter):
                return
            for _ in range(3):
                still_running = bool(running()) if callable(running) else False
                if still_running:
                    if callable(stopper):
                        stopper(0.5)
                    time.sleep(0.05)
                    continue
                if starter():
                    return
                time.sleep(0.1)
            logger.warning("live worker を起こし直せませんでした（塞ぎは解除済み）")
        except Exception as e:
            logger.warning(f"live worker の再開で例外: {e}")
```

呼び出しは「塞ぎを外す 2 か所」= `_reap_fenced_thread`（死を確認した時）と `request_start`（塞ぎを外した時）で、どちらも **GUI スレッド**です。

**聞きたいこと（重要）**

1. `time.sleep(0.05/0.1)` を最大 3 周、**GUI スレッドで**行うため最悪 400ms 前後 UI が固まります。再試行を `after` や inbox 経由の非同期にすべきでしょうか。推奨構造をください。
2. `releaseAll()` は**全所有者**の申告を取り下げます（キーボードやゲームパッドという「人間の入力」の持ち分も含む）。打切り後に人間が押し続けていた場合、その押下が送られなくなります。より狭い `dropOwner(source)` にすべきでしょうか。ただし `_resume_fenced_live` は「逃げたスレッドの送り元」を知りません（封鎖時に runner 側で記録する必要があります）。
3. `releaseAll()` が積む中立 snapshot と、直後の `startLiveWorker` が積む `snapshot()` の二重 push は無駄でしょうか（同じ値なら scheduler の畳み込みに任せて良いか）。

### 4.5 裏スレッドから GUI への受け渡し箱（新規 core/ui_inbox.py）

```python
class UiInbox:
    """裏スレッドから GUI スレッドへの受け渡し。Tk には触らない。"""

    def __init__(self) -> None:
        self._must: queue.SimpleQueue[tuple[Callable[..., Any], tuple[Any, ...]]] = (
            queue.SimpleQueue()
        )
        self._latest: dict[str, tuple[Callable[..., Any], tuple[Any, ...]]] = {}
        self._lock = threading.Lock()

    def post(self, fn: Callable[..., Any], *args: Any) -> None:
        """必ず届ける 1 件を積む（捨てない）。"""
        self._must.put((fn, args))

    def post_latest(self, key: str, fn: Callable[..., Any], *args: Any) -> None:
        """同じ key は最新の 1 件だけ残す（表示の更新向け）。"""
        with self._lock:
            self._latest[key] = (fn, args)

    def drain(self, budget: int = 64) -> int:
        """溜まった分を実行する。GUI スレッドからだけ呼ぶ。"""
        with self._lock:
            latest, self._latest = self._latest, {}
        jobs: list[tuple[Callable[..., Any], tuple[Any, ...]]] = list(latest.values())
        for _ in range(budget):
            try:
                jobs.append(self._must.get_nowait())
            except queue.Empty:
                break
        done = 0
        for fn, args in jobs:
            try:
                fn(*args)
            except Exception:
                # 1 件の失敗で残りを捨てない。規約どおりログは残す。
                logger.exception("GUI への受け渡し処理で例外")
            done += 1
        return done
```

GUI 側は `Window` が 16ms 周期で `drain` を呼びます（`_closing` で再予約を止める）。結線した呼び出し元は serial_panel の 3 か所（bcon 表示＝latest / 切替の後始末＝must / ゲームパッド表示＝latest）と camera_panel の開結果（must）です。camera_panel は「10 秒待って破棄」する期限ループを**削除**しました（古い結果は `_on_camera_opened` が seq で捨てるため）。

**聞きたいこと**

1. `drain` は「latest（表示）→ must（必達）」の順で実行します。カメラの受け渡し（must）が表示更新の後になる点は問題でしょうか。must を先にすべきでしょうか。
2. `budget=64` で打ち切って次の周期へ回す設計は妥当でしょうか。
3. inbox を持たない宿主では従来どおり `after(0, lambda: fn(*args))` へ落とす逃げ道を残しています（テストの偽物対策）。実機経路は必ず inbox を持ちますが、この逃げ道は許容範囲でしょうか、それとも全宿主に inbox を必須にすべきでしょうか。
4. `drain_on_close`（終了時に残った must を引き渡す）を用意しましたが**実際には呼んでいません**。呼ぶべき箇所は終了階段のどこでしょうか。

### 4.7 θ の借用範囲を ε/2 に絞る（motion.py）

**元の欠陥**: 中心付近（`r < DEADZONE_R=8`）の点は θ を隣から借りるが、借りると XY が最大 2r 動く。ε=2.5 でも実測 11.89 の誤差が残り、ランダム 400 本で 45 本が ε 超過（最悪 15.797）。ε の再検証は「最悪時刻に既に waypoint がある」で打ち切るため直せなかった。

```python
def _fill_theta(
    polars: list[tuple[float, float, float]],
    raw_th: list[float],
    borrow_r: float = DEADZONE_R,
) -> list[float]:
    """r が borrow_r 未満の点の θ を、有効な隣の θ で埋める（設計 ID:006）。

    前向きに埋めたあと、後ろ向きの有効値で上書きする。中心付近の θ は
    「意味のない値」なので、倒れてきた/倒れていく先の向きを使う。

    borrow_r を DEADZONE_R より小さくできるのは、θ を借りた点が XY で
    最大 2r 動くためである。借りる範囲を ε/2 以下に限れば、この移動だけで
    ε を超えることはない（_compress_run が min(DEADZONE_R, eps / 2) を渡す）。
    """
    fixed = list(raw_th)
    fwd: float | None = None
    for i, (_t, r, th) in enumerate(polars):
        if r >= borrow_r:
            fwd = th
        elif fwd is not None:
            fixed[i] = fwd
    bwd: float | None = None
    for i in range(len(polars) - 1, -1, -1):
        _t, r, _th = polars[i]
        if r >= borrow_r:
            bwd = fixed[i]
        elif bwd is not None:
            fixed[i] = bwd
    return fixed
```

呼び出し側は `fixed = _fill_theta(polars, raw_th, min(DEADZONE_R, eps / 2.0))`。`compress_track` の docstring は「保証するのは `max(ε, QUANT_FLOOR)`。誤差は 8ms 格子化＋前値ホールド後の track に対して測る」へ直しました。

**実測（修正前 → 修正後）**: repro3 の誤差 11.894 → 0.580 ／ 中心貫通の誤差 11.031 → 0.000 ／ ランダム 400 本の違反 45 → **0**（最悪 15.797 → 0.000）／ waypoint 数は入力の 94.9% → 94.9%（変化なし）。

**聞きたいこと（重要）**

1. 設計 ID:006 の意図は「中心付近の θ を全部隣で置き換えて、中心を貫く動きを直線にする」だったと理解しています。借用範囲を `min(8, ε/2) = 1.25` に狭めると、`1.25 <= r < 8` の点は自分の（暴れ得る）θ を保ちます。**「倒して戻す」ような往復**で waypoint が増えすぎる危険はないでしょうか（私の測定では円 2 点・中心貫通 15 点・ランダム 94.9% で悪化なし）。
2. `_refine_quantized` の打ち切り（「最悪時刻に点がある → break」）はそのままです。根本原因を直した結果として違反 0 になりましたが、将来 ε 超過が出たときのために「既存 waypoint の値を理想値で置き換える」安全網を足すべきでしょうか（別のレビューでは、`ideal` は θ 借用後の値から作られるため置き換えても直らない、と指摘されています）。
3. `QUANT_FLOOR = 1.2` 以下では再検証せず返す仕様はそのままにし、docstring で「保証は `max(ε, QUANT_FLOOR)`」と明示する形にしました。この整理で十分でしょうか。

### 4.8 記録停止時の hold_end 補完（blockly_record.py）

```python
#: 記録停止で解放が無い hold に確保する最短の押下時間（ms）。
#: 8ms スロット 3 つ分。実機で「何 ms あれば押下が認識されるか」を測って確定する。
MIN_HOLD_MS = 3 * 8


def _close_open_holds(steps: list[dict[str, Any]], clip_len_ms: int) -> list[str]:
    """記録停止で解放が無い hold に、クリップ終端の hold_end を補う。

    target ごとに開閉を順に追う（「同じ target の hold_end があるか」だけで
    見ると、hold → hold_end → hold の 2 回目を取りこぼす）。

    補った hold_end は押下から MIN_HOLD_MS を下回らない時刻へ置く。押下が
    終端の直前にあっても、8ms スロットで 1 回も線に出ない事態を避けるため。
    戻り値は補った target（利用者へ知らせるため）。
    """
    open_at: dict[str, int] = {}
    for step in steps:
        if step["kind"] == "hold":
            open_at[str(step["target"])] = int(step["at_ms"])
        elif step["kind"] == "hold_end":
            open_at.pop(str(step["target"]), None)
    for target, at in sorted(open_at.items(), key=lambda kv: kv[1]):
        steps.append(
            {
                "kind": "hold_end",
                "target": target,
                "at_ms": max(int(clip_len_ms), at + MIN_HOLD_MS),
            }
        )
    return list(open_at)
```

呼び出しは `_clip_to_steps` の中、**`at_ms` を剥がして時刻順に並べ替える前**です（後ろだと順序が効きません）。

    if closed:
        # 利用者の次の行動が変わる情報。GUI（LogPane 経由）へ 1 行だけ出す。

### 4.16 採用しなかった案: scheduler での revision 単調性ガード

別のレビューは「`push` で `revision < last` を捨てる」を 1 箇所の門として推奨しました。実装したところ、**既存の契約テストが落ちました**: `test_eb_cadence_stays_discrete_with_16ms_dwell` は revision を 1, 100, 200, 101, 201, … と**意図的に非単調**に積み、60ms 押下＋20ms 離しが融合しないことを検査します。つまり既存スイートの立場は「`push` にとって revision は識別子であり、順序の責任は申告側にある」です。
