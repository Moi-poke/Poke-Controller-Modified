### 2.11 4.12 capability で切る

```python
def raw_serial_for_m(transport: Any) -> Any:
    """M の注入に使ってよい生シリアルを返す。バイナリ方式は常に None。"""
    from core.transport.base import BCON_STATE

    if getattr(transport, "capability", None) == BCON_STATE:
        return None
    getter = getattr(transport, "get_raw_serial", None)
    if callable(getter):
        try:
```

## 3. 採用しなかった 2 点（判断の妥当性を問う）

### 3.1 4.6 の保存順序（保存をシリアル停止より前へ）

**採用しませんでした。** 理由 2 つ。

1. リポジトリの E2E が終了イベントの**完全な順序**を契約として固定しており、設定・統計の保存は `serial_shutdown` の**後**にあります（`tests/test_preview_fps_e2e.py:811-833` の期待列）。
2. `Window._save_settings`（Window.py:770-836）は `com_port` / `com_port_name` / `transport_name` という **Tk 変数**から書いており、serial の生状態を読みません（`self.serial.` の参照は transport_override / sender / keyboard / is_open / shutdown のみ）。「停止後に読むと空で保存される」という前提が成り立ちません。

**聞きたいこと**: この判断は妥当でしょうか。順序を変えるべきなら E2E の期待値も同時に更新する必要があります（そちらが正なら合わせます）。

### 3.2 4.16 の scheduler 単調性門（前回推奨の 1 箇所の門）

**入れず、`putLive` の錠で代替しました。** 前回実装したところ、既存の契約テスト `test_eb_cadence_stays_discrete_with_16ms_dwell` が落ちました（revision を 1, 100, 200, 101, 201, … と**意図的に非単調**に積み、キューとしての cadence を検査しているため）。`push` にとって revision は識別子で、順序の責任は申告側にある、というのが既存スイートの立場です。今回の `putLive` の錠は「申告側が必ず同じ臨界区間で snapshot と push を行う」ことを仕組みで強制するので、今後経路が増えても同じ穴は開きません。

**聞きたいこと**: この代替で十分でしょうか。門を入れるべきなら、cadence テストの revision を単調にしてから入れる形になります。
